> **As built:** the graph panel uses Cytoscape.js, not NVL, because NVL's license doesn't cover Neo4j Community. Read "NVL" below as "the graph library". DESIGN §7 lists every deviation.

## Step 2: Process topology and gate refactor (critical)

The demo runs in two modes, and both must work:

| Mode | Who starts the gate code | HTTP |
|---|---|---|
| **A. Agent run** | Claude Code launches the gate MCP server (stdio) | **Off** in this process (`GATE_HTTP=off` in the plugin's MCP env) |
| **B. UI** | `npm run demo:ui` starts a standalone process | **On**: owns `127.0.0.1:$GATE_PORT` (default 4610) |

Because approvals arrive in process B while the agent waits in process A:
- **`await_approval` must observe decisions through the graph**, not only in memory.
- **Required behavior:** `await_approval` (and the waiting part of `request_approval`) checks `GateDecision.status` for its `gate_id` with a read query every 500 ms until the status ≠ `pending` or the 50-second budget expires.
- If both run in the same process, an in-memory fast path may remain, but **the graph check is the source of truth**.
- `POST /api/gates/:id` performs the DESIGN §4 decision writes (status, Feedback, Override, term activation) with process B's own driver.
- **Concurrency guard:** the POST must only transition `pending → approved | rejected`. Use a conditional write, `MATCH (g:GateDecision {id:$id, status:'pending'}) SET …`, and return 409 if no row matched.
- If T2.5 used in-memory resolution only, refactor it now. Add a test that runs the MCP wait and the HTTP POST **in two separate processes**.
- `demo:ui` must start even if no agent is running (needed for the replay demo, T4.4).

## Step 3: HTTP API

All endpoints are read-only except the gate POST. **All graph reads use a session opened with `defaultAccessMode: READ`** and a 2-second transaction timeout. Bind to `127.0.0.1` only. Disable CORS.

| Method | Path | Response |
|---|---|---|
| GET | `/` | `viz/dist/index.html` (build with Vite; serve `viz/dist/*` statically) |
| GET | `/api/health` | `{ok, neo4j: true\|false, gds: true\|false, providers: {witness, tables:{…}}}` |
| GET | `/api/iterations?deal=` | `[{n, status, started_at}]`, newest first |
| GET | `/api/graph?deal=&iteration=&scene=1\|2\|3` | `{version, nodes[], rels[], witness:{check, eids[]}\|null, truncated: bool}` |
| GET | `/api/gates?deal=` | Existing shape, **extended** with optional `details` (Step 5.2) |
| POST | `/api/gates/:id` | Existing contract; body `{action: approve\|approve_except\|reject, comment?}`; 409 if not pending |
| GET | `/api/tables/:name?deal=&iteration=` | `{status: ok\|unavailable, reason?, columns[], rows[]}` |

**`/api/graph` details**
- `version` is a stable hash of the sorted node and relationship ids plus each node's `status`/`fit_score`/`on_critical_path`. The client skips work when `version` is unchanged. ETag/304 is optional.
- **Node DTO:**
  ```
  {id: elementId, labels[], subgraph, caption, status?, emphasis?}
  ```
  - `subgraph` ∈ {knowledge, evidence, plan, decisions, ontology}, derived from the label map in DESIGN §1.1.
  - `emphasis` ∈ {critical_path, draft, witness}.
- **Relationship DTO:** `{id: elementId, from, to, type}`.
- **Node cap:** 150 per scene (`MAX_SCENE_NODES`). When exceeded, keep the nodes by scene priority (Step 4.1 order) and set `truncated: true`.

**Captions** (computed server-side, ≤ 28 characters, ellipsized):

| Label | Caption |
|---|---|
| Pattern | `name` |
| Task, PlanTask | `summary` |
| Finding | `kind: text` |
| FramedUseCase | `use_case_id` |
| Selection | `uc → pattern` |
| Candidate | `pattern (fit_score)` |
| GateDecision | `gate: status` |
| Feedback | first words of `text` |
| Override | `kind subject` |
| OntologyTerm | `name` |
| CapabilityDecision | `capability_id: outcome` |

## Step 4: Scene queries (`packages/gate/src/ui/scenes/*.cypher`)

Each scene is two queries: a **node-set query** returning one row `{nodes}`, then a shared **relationship query** over those node ids. Every query is parameterized, scoped by `$deal`, and bounded.

### 4.1 Node sets

**Scene 1: Knowledge.** Patterns in play this iteration, their tasks, and related patterns. Priority order: selected patterns, candidates, related patterns, tasks.
```cypher
OPTIONAL MATCH (x)-[:IN_ITERATION]->(:Iteration {deal_code: $deal, n: $iteration})
OPTIONAL MATCH (x)-[:SELECTS|OF]->(p:Pattern)
WITH collect(DISTINCT p) AS pats
OPTIONAL MATCH (p2:Pattern)-[:HAS_TASK]->(t:Task) WHERE p2 IN pats
OPTIONAL MATCH (p3:Pattern)-[:REQUIRES|CONFLICTS|AUGMENTS]-(q:Pattern) WHERE p3 IN pats
RETURN pats + collect(DISTINCT q) + collect(DISTINCT t) AS nodes
```

**Scene 2: Plan.** The current iteration's plan nodes, plus the findings they were framed from and the patterns they select.
```cypher
OPTIONAL MATCH (x)-[:IN_ITERATION]->(i:Iteration {deal_code: $deal, n: $iteration})
WITH collect(DISTINCT x) AS planNodes
OPTIONAL MATCH (fu:FramedUseCase)-[:FRAMED_FROM]->(f:Finding) WHERE fu IN planNodes
OPTIONAL MATCH (s:Selection)-[:SELECTS]->(p:Pattern) WHERE s IN planNodes
RETURN planNodes + collect(DISTINCT f) + collect(DISTINCT p) AS nodes
```

**Scene 3: Decisions.** Human decisions, overrides, and ontology terms, plus what they point at.
```cypher
OPTIONAL MATCH (d) WHERE (d:GateDecision OR d:Feedback OR d:Override) AND d.deal_code = $deal
WITH collect(d) AS decs
OPTIONAL MATCH (t:OntologyTerm) WHERE t.scope IN ['global', $deal] AND t.status IN ['proposed','active']
WITH decs + collect(t) AS anchors
OPTIONAL MATCH (a)-[:DECIDED_ON|ON|CONSTRAINS|RESOLVED_BY|MOTIVATED_BY]->(tg) WHERE a IN anchors
RETURN anchors + collect(DISTINCT tg) AS nodes
```

Every scene starts with `OPTIONAL MATCH`, so an empty or not-yet-planned deal returns one row with an empty list, never zero rows (gotcha 7). If the existing schema uses different relationship names (Step 0, item 6), adapt the queries and record the mapping.

### 4.2 Relationships among the node set
```cypher
MATCH (a)-[r]->(b)
WHERE elementId(a) IN $ids AND elementId(b) IN $ids
RETURN elementId(r) AS id, elementId(a) AS from, elementId(b) AS to, type(r) AS type
LIMIT 600
```

### 4.3 Emphasis
- `draft`: any node with `status = 'draft'`.
- `critical_path`: any PlanTask with `on_critical_path = true` (present after T3.2).
- `witness`: any node whose id is in the witness provider's `eids` (Step 5.3).

## Step 5: Page (`viz/`), panels, and providers

### 5.1 Graph panel (NVL)
- **Dependency:** `@neo4j-nvl/base`, plus the interaction-handlers package for zoom, pan, and drag. Pin exact versions. Consume them from npm and **never vendor them**.
- **Init:** `disableTelemetry: true`. Layout per scene: `hierarchical` for scene 2, `forceDirected` for scenes 1 and 3.
- **Polling:** every 2 seconds, with at most one request in flight; the client skips if `version` is unchanged.
- **Incremental update** (the core logic, unit-tested in isolation):
  1. Diff the previous and new node and relationship sets by id: `added`, `updated` (caption, emphasis, or status changed), `removed`.
  2. Apply `added` and `updated` with NVL's incremental add/update API, and `removed` with its remove-by-id API. **Look up the exact method names in the NVL API docs for the pinned version**, and wrap them in a thin `GraphView` adapter so tests can mock NVL.
  3. **Never** reinitialize or relayout the whole graph during polling. A full reload is allowed **only** when the scene or the iteration changes.
- **Styling:** colors by `subgraph`, matching the deck: knowledge `#9DB8C7`, evidence `#FF9A7A`, plan `#8EE3EA`, decisions `#B79CFF`, ontology `#F4C25A`, witness `#FF5C5C`. Show `draft` nodes with a lighter tint, and `critical_path` nodes and the edges between them with a thicker outline.
- **Witness behavior:** when `witness.eids` changes to a non-empty set:
  1. color those nodes red;
  2. fit or zoom the view to them for 3 seconds, then restore the previous zoom;
  3. show a toast with `witness.check`.
  When the witness becomes null, clear the highlight.
- **Iteration control:** a dropdown fed by `/api/iterations`, with **Follow latest** on by default (it auto-switches when a new iteration appears).

### 5.2 Gate panel (upgrade the T2.5 bare panel)
- **List pending gates for the deal.** Each card shows `gate`, `summary`, and, if present, `details`:
  ```
  details = {candidates: [{pattern, fit_score}], provenance_eids: []}
  ```
- **Extend `request_approval`, backward-compatible:** add an optional `details` argument, stored as a JSON string on the GateDecision. Existing callers keep working.
- **Actions:** Approve, Approve except… (opens a text field), and Reject (comment required). Disable the buttons while the POST is in flight, and show 409 as "already decided."
- **Provenance link:** clicking it highlights `provenance_eids` in the graph panel, using the same mechanism as witnesses but in cyan.
- **New-gate cue:** a badge counter in the header. An optional sound is off by default (config `GATE_SOUND=on`).

### 5.3 Provider seams (so M3 can plug in later)

Add `packages/gate/src/ui/providers.ts`:
```ts
export interface WitnessProvider {
  latest(deal: string, iteration: number): Promise<{ check: string; eids: string[] } | null>;
}
export interface TableProvider {
  name: "buy_vs_build" | "resource_load" | "validators" | "iteration_diff";
  get(deal: string, iteration: number): Promise<
    { status: "ok"; columns: string[]; rows: unknown[][] } |
    { status: "unavailable"; reason: string }>;
}
```

**Default implementations in this task:**

| Provider | Default behavior now | Becomes real when |
|---|---|---|
| `WitnessProvider` | If `graph/validate.ts` (T3.1) exists, run it **on version change only** (not every poll) and return the first failing check's `witness_eids`. Otherwise return `null`, and `/api/health` reports `witness: unavailable`. | T3.1 lands (see amendment A1) |
| `buy_vs_build` | Read `CapabilityDecision` nodes for the deal and iteration. If there are none, return `unavailable: "no decisions yet"`. | T3.6 lands |
| `resource_load` | Sum `PlanTask.weeks_e` grouped by `skill` and `wave`. If `wave` is null everywhere, return `unavailable: "not scheduled yet"`. | T3.2 lands |
| `validators` | Run `graph/validate.ts` if present and list `check`, `examined`, `verdict`. Otherwise `unavailable`. | T3.1 lands |
| `iteration_diff` | Implement the query from DESIGN §5.3 directly (read-only). If iteration < 2, return `unavailable: "needs iteration 2"`. | Works now; data appears with T4.1 |

**Tables panel:** tabs for the four tables. An `unavailable` table shows its reason in a muted empty state, never an error.
